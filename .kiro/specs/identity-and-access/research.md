# 調査記録と設計判断

## 概要

- **機能**: `identity-and-access`
- **ディスカバリ範囲**: 既存機能の拡張に対する軽量ディスカバリ
- **主要な確認結果**:
  - 認証決定表の10ケースは、ログイン画面、フォーム検証、アプリのセッションゲート、および認証 E2E に対応している。
  - 6つの利用者データテーブルは、所有者列、行レベル制御、認証済みロールの権限、および匿名ロールの権限剥奪を共通境界としている。
  - 現行コードに新しい抽象化や依存関係を追加せず、認証 UI とデータ所有者制御を1つのセキュリティ境界として固定するのが最小の設計である。

## 調査ログ

### 認証 UI とセッション境界

- **背景**: 要件 1〜3 が既存コードにどのように実現されているかを確認した。
- **参照元**: `src/features/auth/LoginPage.tsx`、`src/features/auth/validation.ts`、`src/App.tsx`、`src/lib/supabase.ts`、`src/features/auth/validation.test.ts`、`e2e/auth.spec.ts`、`spec/tables/01-auth.jsonl`
- **確認結果**:
  - メールアドレスとパスワードが揃うまで送信できず、メール形式不正時は認証 API を呼ばない。
  - 未登録メールとパスワード不一致は同一メッセージ、通信失敗は別メッセージとして扱う。
  - 初期セッション復元中は保護画面を出さず、認証状態変更を購読してログイン画面と保護領域を切り替える。
  - ログアウト成功と保存セッション喪失は認証状態変更を通じてログイン画面へ反映される。
- **設計への影響**: `LoginPage`、純粋な入力検証、`App` のセッションゲートを独立責務として維持する。ログイン成功時の画面切替は認証イベントを唯一の接続点とし、認証画面から保護画面への直接ルーティングを追加しない。

### 所有者境界と権限

- **背景**: UI の認証だけでなく、直接データアクセスでも別利用者の情報を隔離できることを確認した。
- **参照元**: `supabase/migrations/20260829000000_init.sql`、`20260830000000_import_material.sql`、`20260831000000_grants.sql`、`20260901000000_revoke_rpc_from_anon.sql`、`20260902000000_harden_functions.sql`、`20260903000000_material_summary.sql`、`20260904000000_sync_active_keywords.sql`、各 feature の `api.ts`、`e2e/auth.spec.ts`
- **確認結果**:
  - `subjects`、`materials`、`chapters`、`keywords`、`keyword_stats`、`answer_logs` はすべて `owner_id` を必須とする。
  - 6テーブルの認証済みロール向けポリシーは、参照条件と書込検査の双方で `owner_id` と現在の利用者を一致させる。
  - 匿名ロールからテーブル権限を剥奪し、3つの業務 RPC は認証済みロールとテスト用特権ロールだけに実行を許す。
  - E2E は別利用者の科目が一覧にも直接 URL にも現れないことを確認する。
- **設計への影響**: 各 feature API は利用者 ID を所有者列へ設定するが、最終的な認可判断はデータ層の所有者ポリシーへ一元化する。下流機能は独自の認可規則でこの境界を置き換えない。

### 実装と検証の差分

- **背景**: ベースライン完了を過大評価しないため、コード、設定、決定表、テストの不一致を調べた。
- **参照元**: `supabase/config.toml`、`docs/仕様書.md`、`e2e/auth.spec.ts`、各 migration
- **確認結果**:
  - UI はサインアップ導線を持たない一方、ローカル設定のメールサインアップは有効である。本仕様は既存 UI の「導線を提供しない」契約だけを所有し、外部 Auth 設定による登録禁止までは既存保証としない。
  - セッション失効 E2E は保存トークン削除後の再読み込みを検証する。データ操作中の 401 や更新トークン失敗に専用メッセージを出す経路は確認できない。
  - 別利用者データの読取拒否は E2E があるが、所有者偽装書込の拒否および匿名ロールのテーブル／RPC 拒否は migration の実装証拠に留まり、独立した統合テストはない。
- **設計への影響**: 設計は既存保証を越えてエラー UI やサーバー設定を約束しない。タスクでは実装済み項目と、未検証の防御的テスト項目を区別する。

## アーキテクチャパターン評価

| 選択肢 | 概要 | 強み | リスク／制約 | 判断 |
|---|---|---|---|---|
| 現行の二重境界を維持 | クライアントのセッションゲートとデータ層の所有者制御を組み合わせる | UI と直接データアクセスの両方を保護し、既存構造と一致する | 両境界の回帰検証が必要 | 採用 |
| クライアントだけで所有者を絞る | 各問い合わせへ所有者条件を追加する | 画面コードから意図が見えやすい | 直接アクセスや条件漏れを防げない | 不採用 |
| 専用アプリサーバーを追加 | サーバーで認証と認可を仲介する | 中央集約できる | 現行アーキテクチャと対象範囲を越える | 不採用 |

## 設計判断

### 判断: 認証 UI と所有者分離を1つの上流境界として扱う

- **背景**: 全保護画面とデータ feature が同じ利用者セッションと所有者境界へ依存する。
- **代替案**:
  1. UI 認証とデータ認可を別仕様にする。
  2. 両方を1つの `identity-and-access` 仕様で固定する。
- **採用案**: セッションの有無による画面境界と、現在利用者によるデータ境界を1つの上流契約にする。
- **理由**: 一方だけでは利用者間分離を保証できず、変更時には常に両方の整合を再確認する必要がある。
- **トレードオフ**: フロントエンドと DB の双方を同じ仕様で追跡する必要があるが、責務の重複を防げる。
- **追跡事項**: 認証イベント、所有者ポリシー、ロール権限のいずれかが変わる場合、全下流仕様を再検証する。

### 判断: プラットフォーム標準を採用し独自認証層を作らない

- **背景**: メール／パスワード認証、セッション永続化、認証状態イベント、行レベル制御が現行基盤で提供されている。
- **代替案**:
  1. 独自トークン管理と認可サービスを構築する。
  2. 既存の認証クライアントと DB ポリシーを採用する。
- **採用案**: Supabase Auth のクライアント契約と PostgreSQL の RLS／権限を継続利用する。
- **理由**: 既存実装とテストに一致し、重複するセキュリティ実装を増やさない。
- **トレードオフ**: 認証イベントとロール意味論に依存する。
- **追跡事項**: 依存パッケージ更新時にセッション復元、エラー分類、認証イベントの契約を再確認する。

### 判断: 検証関数だけを純粋ロジックとして分離する

- **背景**: 入力検証とネットワーク失敗分類は DOM や認証 SDK なしで検証できる。
- **採用案**: `validation.ts` の小さな関数を維持し、単一実装しかない認証サービスの抽象層は追加しない。
- **理由**: ユニットテスト可能性を確保しつつ、仮想的な差し替えのための層を避ける。
- **トレードオフ**: 認証 SDK 呼び出しは `LoginPage` に残る。
- **追跡事項**: 認証方法が増える場合にだけ feature 内サービス境界を再評価する。

## リスクと緩和策

- ローカルの公開サインアップ設定が有効 — UI 非提供のベースラインとサーバー側登録禁止を混同せず、後者を導入する場合は別途仕様変更する。
- データ操作中のセッション失効に専用処理がない — 現行は認証状態イベントによる保護画面閉鎖だけを契約とし、エラー UX 拡張は隣接仕様と合わせて設計する。
- 書込ポリシーと匿名 RPC 拒否の統合テストがない — `tasks.md` に未完了の防御的検証タスクとして残す。
- 権限変更が全 feature へ波及する — migration 変更時は6テーブルと全公開 RPC、および下流仕様を横断して再検証する。

## 横断レビュー追補（2026-10-10）

- 固定の既存3 RPC だけを検査すると、新規 RPC の anon grant や owner 分離を見逃す。公開 user-data RPC の列挙テストと、下流仕様が利用する4主体 harness を `RpcSecurityMatrix` として一般化した。
- migration と業務 payload は各下流仕様が所有し、identity は grant／RLS／role の検証手順だけを所有することでファイル境界の重複を避ける。
