# 開発環境とブランチ運用

## 1. ブランチ

`main` 一本。履歴は一直線に保つ。

```text
main   常にデプロイ可能な状態を保つ。ここに直接コミットする
```

- 作業がひと区切りついたら `main` に直接コミットする
- コミット前に `npm run typecheck` と `npm test` を通す。振る舞いを変えたときは `npm run test:e2e` も
- コミットは1つの意図につき1つ。決定表の列を足したなら、その実装とテストまで含めて1つにする
- push すると CI（型・ユニットテスト・決定表のカバレッジ）と配信が走る

数日にわたる作業や、途中で `main` を動かしたくない実験だけブランチを切る。
名前は `feat/` `fix/` `chore/` `docs/` を接頭辞にし、戻すときは
`git rebase main` で追いつかせてから **早送りで**取り込む。

```bash
git switch main
git merge --ff-only feat/xxx
git branch -d feat/xxx
```

`--no-ff` は使わない。1コミットのブランチを `--no-ff` で取り込むと、同じ内容の
コミットとマージコミットが並ぶだけで、後から履歴を読む助けにならない。

Pull Request も通さない。開発者が1人でレビューする相手がいないため、PR は
「自分で開いて自分でマージする」だけの手数になる。差分を読み直したいときは
コミット前に `git diff` を読む。

develop も置かない。デプロイ先が1つで開発者が1人のため、`main` と同期を取り
続けるだけの2つ目の `main` になる。

## 2. ローカル DB（Supabase）

開発用の DB はローカルに立てる。本番の Supabase プロジェクトには開発中のコードから一切触れない。

### 2.1 必要なもの

- Docker Desktop（起動しておく）
- Node.js（`.nvmrc` の版）

バージョンはリポジトリに固定してある。

| 対象 | 固定の仕方 | ファイル |
| --- | --- | --- |
| Node.js | `.nvmrc` に版を書く。`package.json` の `engines` で下限も示す | `.nvmrc` |
| Supabase CLI | `devDependencies` に版を固定する | `package.json` / `package-lock.json` |

nvm を使っているなら `nvm use` で `.nvmrc` の版に切り替わる。CI も同じファイルを読む。

### 2.2 起動

```bash
npm install     # 初回のみ。固定された Supabase CLI が入る
npm run db:start
```

初回は Docker イメージの取得に時間がかかる。起動すると次が使える。

| 用途 | URL |
| --- | --- |
| API | http://127.0.0.1:54321 |
| DB | postgresql://postgres:postgres@127.0.0.1:54322/postgres |
| Studio（管理画面） | http://127.0.0.1:54323 |
| 受信メール確認 | http://127.0.0.1:54324 |

`npm run db:status` で URL と anon key を確認できる。`.env.example` を `.env.local` にコピーし、anon key を書き写す。

停止は `npm run db:stop`。データごと消すときは `npm run db:stop -- --no-backup`。

### 2.3 スキーマ

スキーマは `supabase/migrations/*.sql` で管理する。`npm run db:start` のときに順に適用される。

変更するときは新しいマイグレーションを足す。既存のファイルは書き換えない。

```bash
npm run db:migration add_something   # 空のファイルを作る
npm run db:reset                     # DB を作り直してマイグレーションを全て当て直す
```

本番へは `npx supabase db push` で同じマイグレーションを適用する。

### 2.4 開発用のユーザーを作る

本番はサインアップを閉じているが、ローカルでは開いてある（`supabase/config.toml`）。
Studio の Authentication > Users から手動でユーザーを1つ作り、それでログインする。確認メールは無効にしてあるので、作った直後から使える。

## 3. 環境の切り替え

| 環境 | DB | 設定 |
| --- | --- | --- |
| ローカル開発 | `npm run db:start` のローカル | `.env.local` |
| 本番 | Supabase のクラウドプロジェクト | GitHub Actions の Variables / Secrets |

`.env.local` はコミットしない（`.gitignore` で除外済み）。

## 4. CI

`.github/workflows/ci.yml` が Pull Request と `main` への push で走る。
決定表の生成（列番号の重複や同じ列での行の重複があれば失敗する）、決定表のカバレッジ、
型検査、ユニットテストを回す。E2E はローカルの Supabase が要るため CI では回らない。

`.github/workflows/deploy.yml` が `main` への push で GitHub Pages へ配信する。
本番の用意と配信の流れは [本番デプロイ.md](本番デプロイ.md) に書いてある。
