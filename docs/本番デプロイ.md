# 本番デプロイ

配信先は GitHub Pages、DB は Supabase のクラウドプロジェクト。
`main` に入ったものが自動で配信される（`.github/workflows/deploy.yml`）。

## 1. 置き場所

| 何を | どこに |
| --- | --- |
| 画面（静的ファイル） | GitHub Pages のサブパス `https://<ユーザー名>.github.io/blank-study/` |
| DB・認証 | Supabase のクラウドプロジェクト |
| 接続先の値 | GitHub リポジトリの Actions secrets |

サブパスで配信するため、Vite の `base` とルータの `basename` を合わせてある
（`vite.config.ts` の `base: '/blank-study/'`）。リポジトリ名を変えるときは
`base` も同じ名前に直す。合っていないと JS と CSS が 404 になる。

## 2. 初回に用意するもの

### 2.1 GitHub リポジトリ

```bash
gh repo create blank-study --private --source=. --remote=origin
git push -u origin main
```

Settings > Pages > Source を **GitHub Actions** にする。

### 2.2 Supabase プロジェクト

ダッシュボードでプロジェクトを作り、ローカルと同じマイグレーションを適用する。

```bash
npx supabase login
npx supabase link --project-ref <プロジェクトの ref>
npx supabase db push
```

`supabase/migrations/*.sql` が順に適用される。ローカルと本番で同じファイルを使う。

Data API から触れる範囲は `20260831000000_grants.sql` で明示してある。
プロジェクトの Security で「Automatically expose new tables」を切っていても、
テーブルの権限はこのマイグレーションが与えるので、ローカルと同じように動く。

### 2.3 認証の設定

ダッシュボードの Authentication で次のようにする。

| 場所 | 設定 |
| --- | --- |
| Providers > Email | Enable signup を **OFF** |
| URL Configuration > Site URL | `https://<ユーザー名>.github.io/blank-study/` |

アプリにサインアップ導線は無い（決定表「認証」）。利用者は Authentication > Users >
Add user で1件ずつ作り、Auto Confirm User を有効にする。
ローカルの `supabase/config.toml` はサインアップを開けてあるが、これはローカル専用の設定で
本番には影響しない。

### 2.4 接続先の値

リポジトリの Settings > Secrets and variables > Actions に2つ登録する。

| 名前 | 値 |
| --- | --- |
| `VITE_SUPABASE_URL` | `https://<ref>.supabase.co` |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | 上部の Connect、または Project Settings > API Keys の公開キー |

キーの呼び名は Supabase 側で anon key から publishable key に変わった。
古い名前の `VITE_SUPABASE_ANON_KEY` でも読むので、プロジェクトが出しているほうの
名前で登録すればよい。

公開キーはビルド成果物に含まれる。公開前提のキーで、行単位のアクセス制御
（`owner_id = auth.uid()` の RLS）で他人のデータには触れない。
service_role キーは RLS を迂回するため、リポジトリにも Actions にも置かない。

## 2.5 本番 DB につないで手元で確かめる

`.env.production.local` に本番の接続先を書き、`npm run dev:prod` で開く。
`.env.local`（ローカルの Supabase）より優先されるので、書き換えも戻しもいらない。

```
VITE_SUPABASE_URL=https://<ref>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<公開キー>
```

E2E は `.env.local` を読むため、この状態でも本番には触れない。

## 3. ふだんの配信

`main` への push（または Actions の手動実行）で `deploy.yml` が走る。

1. `npm ci`
2. `npm run build`（secrets の接続先を埋め込む）
3. `dist/index.html` を `dist/404.html` にも置く。直接開いた URL を SPA に返させるため
4. Pages へ配信

配信は1つずつ走り、走っているものは走り切らせる（`concurrency: pages`）。

`deploy.yml` はテストを実行しない。テストは `ci.yml` が Pull Request と `main` への
push で回す（型検査・ユニットテスト・決定表のカバレッジ）。E2E はローカルの Supabase が
要るため CI では回らず、手元で `npm run test:e2e` を通してからマージする。

## 4. スキーマを変えるとき

既存のマイグレーションは書き換えない。新しいファイルを足す。

```bash
npm run db:migration <名前>   # 空のファイルができる
npm run db:reset              # ローカルを作り直して全部当て直す
npx supabase db push          # 本番へ同じものを適用する
```

画面より先に DB を変える。列を消す・型を変えるといった後戻りできない変更は、
先に新しい列を足して両方が動く状態にしてから、古い列を消す手順に分ける。
